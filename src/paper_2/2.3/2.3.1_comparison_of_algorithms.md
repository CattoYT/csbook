## The theory of algorithms
- The code you write will always be an **implementation** of an algorithm.
- There are a number of steps you need to take when creating an algorithm: defining inputs and outputs,
and mapping the inputs such that if the same set of inputs are given, the same set out outputs will be produced
(predictability).
- The set of possible inputs is known as the **domain** (like in maths), and the range of possible outputs
is known as the **codomain**. The algorithm can be thought of as a function (f(x)) that converts domain values into codomain values.
- Standard design tools for showing the mapping of inputs to outputs are **flowcharts** and **pseudocode**. 
- These tools allow the design to show the key steps of the algorithm (main techniques, data structures, variables, desicions, and processes).
- Once the algorithm is written, we have to check that the algorithm gives a predictable and repeatable output that is correct for the domain: this is the point of **trace tables**.

## Efficiency
- Algorithms should be made efficient: they should be optimal in terms of **space** (system resources)
and **time**.
- Time complexity can be represented using Big O notation: this is written as O(complexity). For example, O(n²) means that the time the algorithm takes is roughly proportional to the square of the size of the inputs. This is considered a fairly bad time complexity, and the absolute best is O(1), where the algorithm takes the same amount of time no matter the size of the input.
- Time complexity is usually improved by using less steps in the algorithm.
- Space complexity can be improved by loading less things into RAM (less variables, reusing code, etc).
- The third component that makes up efficiency is **scalability**: how does the time and space complexity change as the number of inputs are changed?.


## Big O Notation
Big O notation is a mathematical notation used to describe the **upper bound** of an algorithm's running time or space requirements in **terms of the size of the input data**. It provides a way to classify algorithms based on their performance and efficiency.
Common Big O notations include:
  - O(1): Constant time complexity
  - O(log n): Logarithmic time complexity
  - O(n): Linear time complexity
  - O(n log n): Linearithmic time complexity
  - O(n²): Quadratic time complexity
  - O(2<sup>n</sup>): Exponential time complexity
  - O(n!): Factorial time complexity

>[!NOTE]
Big O notation ignores constant factors and lower-order terms, focusing on the dominant term that grows the fastest as the input size increases (e.g. if an algorithm has a time complexity of O(n^2 + n), it is simplified to O(n^2) because n^2 grows faster than n as n increases).

Every time we run an algorithm, there is a **best case**, **average case**, and **worst case** scenario. The best case is the scenario where the algorithm performs the least number of steps, while the worst case is where it performs the most. The average case is a statistical average of all possible scenarios.

### Time Complexity Examples
Illustrating Big O with the time complexity of bubble sort and binary search:

**Bubble Sort**:

| Case | Description | Time Complexity |
|------|-------------|-----------------|
| Best Case | The list is already sorted. | O(n) |
| Worst Case | The list is in reverse order. | O(n²) |
| Best case for 1000 items | 1 pass, containing 999 comparisons | O(999) |
| Average case for 1000 items | 500 passes, each containing 999 comparisons | O(499,500) |
| Worst case for 1000 items | 1000 passes, each containing 999 comparisons | O(999,000) |

This gives bubble sort a O(n^2) time complexity, as the number of comparisons is roughly proportional to the square of the input size.

**Binary Search**:

| Case | Description | Time Complexity |
|------|-------------|-----------------|
| Best Case | The target value is found in the middle of the list. | O(1) |
| Worst Case | The target value is not in the list, requiring log2(n) comparisons. | O(log n) |
| Best case for 1000 items | 1 comparison | O(1) |
| Average case for 1000 items | log2(1000) ≈ 10 comparisons | O(10) |
| Worst case for 1000 items | log2(1000) ≈ 10 comparisons | O(10) |

This gives binary search a O(log n) time complexity, as the number of comparisons grows logarithmically with the input size.

Merge sort is another example of an efficient sorting algorithm with a time complexity of O(n log n). It divides the input list into smaller sublists, sorts them, and then merges them back together. In its case, the best, average, and worst-case time complexities are all O(n log n), because the list always needs to be divided and merged, regardless of the initial order of the elements.

>[!TIP]
Most divide and conquer algorithms have a log n or n log n in their time complexity, as they repeatedly divide the input data into smaller parts. n log n happens where there is also a linear operation (like merging) that needs to be performed on each of the divided parts.

### Space Complexity Examples
**Space complexity** refers to the amount of memory an algorithm uses in relation to the size of the input data. It is important to consider space complexity when designing algorithms, especially for large datasets or memory-constrained environments. Here are some examples of space complexity for common sorting algorithms:

| Algorithm | Space Complexity | Description |
|-----------|-----------------|-------------|
| Bubble Sort | O(1) | In-place sorting algorithm that requires a constant amount of additional memory for its few variables. |
| Merge Sort | O(n) | Requires additional space for temporary arrays used during the merging process. |
| Quick Sort | O(log n) | In-place sorting algorithm that uses a stack for recursive calls, which requires logarithmic space in the average case. |
